# Live smoke tests

Opt-in tests that call a real GitLab instance through the SDK. `mvn verify` never runs them.

**Status: no area has been run live yet.** The tests compile and are skipped without a token, but no token for a GitLab
instance was available when they were written, so none of them has ever run. Every area below is covered by unit tests
only until someone runs `mvn -Psmoke verify` and records the result here.

## Setup

Use a sandbox project, as the smoke tests of
[gitlab-rest-client](https://github.com/piotr-janczukowicz/gitlab-rest-client/blob/main/docs/guide/smoke-tests.md) do: a
project that holds nothing else, whose path contains `smoke`. The tests refuse any other project, and a numeric id.

| Variable | Meaning |
|---|---|
| `SMOKE_GITLAB_TOKEN` | A personal access token with the `api` scope of a user who owns the sandbox project |
| `SMOKE_GITLAB_PROJECT` | The path of the sandbox project, `group/name`; the path must contain `smoke` |
| `SMOKE_GITLAB_URL` | The instance root; default `https://gitlab.com` |
| `SMOKE_GITLAB_USER_ID` | Optional. The numeric id of a second user who may be added to and removed from the sandbox; without it the add, change and remove of a member is skipped |
| `SMOKE_GITLAB_GROUP` | Optional. The path of a sandbox group, which must contain `smoke` like the project path; without it `GroupLabelsSmokeIT` and the group tests of `VariablesSmokeIT`, `WikisSmokeIT` and `AuditEventsSmokeIT` are skipped. The token's user must be allowed to create labels, variables and (on Premium) wiki pages in it, and needs the Owner role for the lookup of one group audit event in `AuditEventsSmokeIT` (without it that step is skipped) |

```bash
export SMOKE_GITLAB_TOKEN=glpat-...
export SMOKE_GITLAB_PROJECT=my-group/my-project-smoke
export SMOKE_GITLAB_URL=https://gitlab.example.com   # optional, https://gitlab.com is the default
export SMOKE_GITLAB_USER_ID=1234                     # optional, a second user for the member test
export SMOKE_GITLAB_GROUP=my-group-smoke             # optional, a sandbox group for the group tests
```

## Run

```bash
mvn -Psmoke verify
mvn -Psmoke verify -Dit.test=CodeSmokeIT
```

Without `SMOKE_GITLAB_TOKEN` and `SMOKE_GITLAB_PROJECT`, every smoke class is skipped, not failed. Without
`SMOKE_GITLAB_GROUP`, only `GroupLabelsSmokeIT` and the group test of `VariablesSmokeIT` are skipped.

## What is covered

| Class | Area |
|---|---|
| `ProjectsSmokeIT` | load and refresh the sandbox, 404 on a missing project; the group of the sandbox, its projects and subgroups (skipped when the sandbox lives in a user namespace); the signed-in user, a user by id, 404 on a missing user. Archive, unarchive and delete of a project are not run live, because they would change the sandbox |
| `IssuesSmokeIT` | create, comment, edit a note, list notes, update, close, reopen, reload and delete an issue; create, update and delete a label and apply it to an issue; on throwaway issues: participants, estimate and book time, reset both, and link two issues, load and delete the link; 404 on a missing issue |
| `MergeRequestsSmokeIT` | on a throwaway branch with one new file: create, comment, edit a note, list notes, update, close, reopen, reload and delete a merge request, list its commits, its diffs, its diff versions and its participants, set an estimate, add spent time and reset both (time stats), start a rebase and reload the merge request to read `isRebaseInProgress()` (skipped when the sandbox forbids it; that the call returns before the rebase finishes is covered by a unit test only, not verified live), list the merge requests of the instance; create a draft note on it, update it, list the draft notes, delete it; 404 on a missing merge request. Merging and approving are not run live, because the sandbox settings may forbid them and a merge cannot be undone. Publishing a draft note is not run live either, because it would leave a real note |
| `TagsAndReleasesSmokeIT` | create the tag `smoke-<runId>-tag` from the default branch (skipped when the sandbox has none), load it and read `isProtected()`; create a release on it, update the release name, add a link, list the links, load the release through the tag, delete the link, the release and the tag. Needs a role that may create tags and releases (see below). `collectEvidence()` is not run live |
| `MilestonesSmokeIT` | create a project milestone `smoke-<runId>-milestone`, update its description, start date and due date and check that the dates come back as the same `LocalDate`s, close, reopen, reload, read its issues and merge requests (none are assigned, so both are empty), delete it. Promoting a milestone and group milestones are not run live |
| `DiscussionsSmokeIT` | on a throwaway issue: start a discussion, reply, list, refresh; resolve and unresolve only when GitLab reports the thread as resolvable, otherwise assert that it is not. Merge request discussions are not run live |
| `ReactionsSmokeIT` | on a throwaway issue: react with `thumbsup`, list the reactions, delete the reaction. Reactions on notes and merge requests are not run live |
| `GroupLabelsSmokeIT` | needs `SMOKE_GITLAB_GROUP`: create a group label `smoke-<runId>-group-label`, update its description and color, subscribe, unsubscribe, list, reload, delete it. A second test promotes a throwaway project label with `Label.promote()` and checks the group label; it runs only when the sandbox project lives directly in the sandbox group, and is skipped otherwise |
| `PipelinesSmokeIT` | list, load and refresh pipelines and list their jobs, list and load jobs, 404 on a missing pipeline. Reads only, and skipped when the sandbox has no pipelines or jobs: creating, retrying, cancelling and deleting pipelines and retrying, cancelling, playing and erasing jobs need a CI configuration and runners, so they are not run live |
| `CodeSmokeIT` | a file with non-ASCII text (`zażółć gęślą jaźń ✓`) on a throwaway branch: create, read back with `text()` and `bytes()`, update, read, delete, 404 on a missing file; create, protect, unprotect and delete a branch; list and load commits; 404 on a missing branch; the root tree of the default branch is not empty, a recursive tree contains the created file's path, a straight compare of the default branch with a branch that has one more commit lists that commit, and the blame of the created two-line file returns its two lines, and the merge base of the two branches loads with a SHA (only these are asserted) |
| `ManagementSmokeIT` | create a project named `smoke-<runId>-project` in the namespace of the sandbox (the namespace id is read from the sandbox, so the token's user must be allowed to create projects there), update its description, reload it, list its forks and shared groups, delete it; list the forks and shared groups of the sandbox. Creating and deleting a **group** is not run, because it needs the right to create groups, which a sandbox token may not have; updating the sandbox itself is not run either. Transfer, fork, share, unshare and deleting the sandbox are not run live, because they would change or lose the sandbox. GitLab.com may keep a deleted project for a while before it disappears |
| `MembersSmokeIT` | list the direct and all members of the sandbox, find the signed-in user among them, load and refresh a member by user id, 404 on a user who is not a member. With `SMOKE_GITLAB_USER_ID` set (and that user not yet a direct member): add the user as Developer, change the level to Reporter, reload, remove. Access requests are not run live |
| `WebhooksSmokeIT` | create a webhook with the URL `https://example.com/smoke-<runId>`, update its name and replace its events with pipeline events only (push switched off), reload, list, delete, 404 on a missing hook. `Webhook.test(...)` is **not** run live, because it makes GitLab send a real HTTP request to the hook URL. Group webhooks (Premium) are not run live |
| `DeploySmokeIT` | add a deploy key (a fixed public key made for the tests, titled `smoke-<runId>`), update its title and push flag, reload, list, delete; create a deploy token with `READ_REPOSITORY`, check that the secret is present and absent from `toString()` (it is never printed), reload, list, delete; 404 on a missing key. Needs a Maintainer. GitLab accepts a key only once, so a run that failed to delete the key blocks the next run until you remove the key by hand |
| `ProtectionSmokeIT` | create the branch `smoke-<runId>/protected` from the default branch (skipped when the sandbox has none), protect it for Maintainers, allow force pushes, reload, list, unprotect, delete the branch; protect the tag pattern `smoke-<runId>-*` for Maintainers, reload, list, unprotect; 404 on a branch and a tag that are not protected. Needs the Maintainer role. Group protected branches (Premium) are not run live |
| `VariablesSmokeIT` | create a project variable `SMOKE_<RUNID>`, update its value, reload, move it to a NEW environment scope `smoke-<runId>-scope`, then create a second variable of the same key in the scope `*` and update, load and delete it, checking that the first one is untouched (this is the scope targeting); delete the first one. Asserts that no `toString()` of the SDK objects prints a value. With `SMOKE_GITLAB_GROUP`: create, update, reload, list and delete a group variable `SMOKE_<RUNID>_G`, otherwise that test is skipped. Masked and hidden variables are not run live |
| `EnvironmentsSmokeIT` | create an environment `smoke-<runId>-env`, update its tier, description and Kubernetes namespace, clear the namespace, reload, list, stop, wait up to 60 seconds for the state `stopped` (otherwise the delete step is skipped and reported as a failure, and the cleanup tries again), delete it. A second environment `smoke-<runId>-deploy-env` gets two deployments of the newest commit of the default branch (skipped when the sandbox has no default branch or no commit): create one as running and set it to success, create one as success, list, load, delete the older one; the other goes with the environment. Approving and rejecting a deployment (Premium) are not run live |
| `SchedulesSmokeIT` | create a pipeline schedule `smoke-<runId>-schedule` on the default branch (skipped when it has none) that fires once a year, switch it off and set its time zone, add a schedule variable and update it, load, reload, list, delete the variable and the schedule, read `lastPipeline()` (empty); create a pipeline trigger `smoke-<runId>-trigger`, check that its token is present and absent from `toString()`, update its description, reload, list, delete. `play()`, `takeOwnership()` and firing a trigger are not run live, because they start a pipeline or change the owner |
| `RunnersSmokeIT` | reads only, skipped when the sandbox project has no runner: list the runners of the sandbox, load one with `sdk.runner(id)`, refresh it, read `tagList()`, `type()`, `typeName()`, the status, the managers and the jobs (a 403 or 404 on the list, the managers or the jobs skips the test). Registering, updating, enabling, disabling and deleting a runner and resetting a token are not run live |
| `ArtifactsSmokeIT` | reads only, skipped when none of the latest 50 jobs of the sandbox has artifacts: list the artifact tree (the root and one directory, recursively), download the archive to a temporary directory that is emptied and deleted afterwards (skipped when GitLab reports no size or more than 50 MB; a 403 or 404 on the first artifact read skips). Keeping and deleting artifacts are not run live |
| `PackagesAndRegistrySmokeIT` | reads only, each test skipped when the sandbox has no package or no registry repository, or when the first list answers 403 or 404 (the feature is disabled): list the packages, load and reload one, list its files; list the repositories, reload one, list its tags and load the first. Downloading a package file and every delete are not run live |
| `WikisSmokeIT` | create a wiki page titled `smoke-<runId>/page` (a slug with a slash), find it by its slug, update its content, then its title to `smoke-<runId>/renamed` and check that the page comes back with a new slug, find it by the new slug, list, reload, delete. With `SMOKE_GITLAB_GROUP` (Premium; the test is skipped on a 403 or 404): create, find and delete a group page `smoke-<runId>/group-page`. Uploading an attachment is not run live, because GitLab offers no call that removes an uploaded file |
| `SnippetsSmokeIT` | in the sandbox project: create a private two-file snippet titled `smoke-<runId>` through the payload overload, find it, read its content and one file on the ref `main` (that check is skipped when GitLab answers 404), update it (add a file, move a file with its previous path, delete a file), reload it and check its files, delete it. Personal snippets live on the token user's account, outside the sandbox, so that test is **read-only**: list the user's snippets and load the first one (skipped when the user has none). Creating, updating and deleting a personal snippet are covered by unit tests only, not run live; public and internal visibility are not run live either |
| `DependenciesSmokeIT` | reads only (Ultimate), skipped when the first list answers 403 or 404 or when the list is empty (the sandbox needs a dependency scan result): list the first five dependencies of the sandbox, read the accessors of the first, and list again filtered by its package manager. It has not been run live yet |
| `AuditEventsSmokeIT` | reads only (Premium; nothing in the smoke tests writes an audit event on purpose), skipped when the first list answers 403 or 404 or when the list is empty: list the first five audit events of the sandbox and check they come newest first, list the events of the day before the newest one's creation time (bounds truncated to whole seconds), expecting it first, and last find the newest by its id. With `SMOKE_GITLAB_GROUP`: the same for the group; its lookup by id needs the Owner role, and a token without it is expected to get a 403, which skips the lookup after the list checks have run. It has not been run live yet |

Every resource a test creates is named `smoke-<runId>-...` (a variable key is `SMOKE_<RUNID>`, a wiki page title is
`smoke-<runId>/...`, so its slug holds a slash, and a snippet title is `smoke-<runId>`) and is removed in a
`finally` block, so a failed run leaves nothing behind. Issues are deleted outright. Cleanup relies on the same SDK
calls that the tests exercise, so a failure in `delete()` can leave a `smoke-` resource in the sandbox; remove it by
hand. GitLab may keep a deleted resource for a short time before it disappears.

A disabled feature or a 403 skips, never fails: the first call of an area that may be switched off for the sandbox or
refused to the token (packages, the container registry, environments, CI/CD variables, schedules and triggers, runners
and their managers and jobs, job artifacts, project and group wikis, project and personal snippets, project
dependencies, project and group audit events) goes through `SmokeSkips.probe(...)`, which turns GitLab's 403 or 404 into
a skipped test. The calls under test do not, so a wrong request still fails.

## Not yet verified live

All of it. Besides the areas listed above as not run live, none of the covered calls has met a real GitLab yet, so these
questions are open until a run:

| Question | Why it matters |
|---|---|
| Repository reads beyond the smoke test | `RepositoryFile.blame()` sends the range `1` to the line count, which GitLab is expected to accept; the smoke test is the first check, and its result is not verified live yet. Contributors, `changelog`, `deleteMergedBranches` and the tree of a nested path are not run live |
| Non-ASCII file content through the multipart form | A unit test proves the form carries the UTF-8 bytes of the text without a charset of its own, which is what RFC 7578 expects. `CodeSmokeIT` is the test that checks GitLab reads it back unchanged |
| Tier-gated calls (for example approvals) | They depend on the tier of the instance; the SDK adds no tier logic, and the core's tier guard applies only when a tier is configured |
| Multipart project and group create and update on a real instance | The form field names and the boolean and non-ASCII values are only unit-tested. `ManagementSmokeIT` is the first check of project creation and update; group creation and update have no smoke test |
| The expiry of a member as an `Instant` | The SDK sends the date as the start of that day in UTC and reads an ISO date back; whether GitLab accepts and returns exactly that is unchecked, because `MembersSmokeIT` does not set an expiry |
| Clearing a description with an empty string | `clearDescription()` on issue and project updates, and `description("")` on the other update builders, send an empty string; that GitLab then clears the description is unchecked, because no smoke test sends one |
| Clearing the expiry of a member | `clearExpiresAt()` sends `"expires_at": null`; that GitLab accepts it and then returns no expiry is unchecked, because `MembersSmokeIT` does not set or clear an expiry |
| The shape of the protected-branch access arrays | The role-based rules are read from the arrays GitLab returns and a level is sent for each push, merge or create rule; `ProtectionSmokeIT` is the first check, including that user- and group-based rules never show up as role rules |
| The deploy token secret is shown once | The SDK relies on the secret being in the create answer only; `DeploySmokeIT` checks the create answer but not that a later load omits it |
| Hook URL validation by GitLab | GitLab validates the URL of a webhook (for example that its host resolves and is not a local address); `WebhooksSmokeIT` uses `https://example.com/smoke-<runId>` and never calls `test()`, so whether GitLab accepts that URL is checked only on the first live run |
| Calls that need permissions beyond `api` on a project | Protecting a branch needs the Maintainer role; a token of a lower role fails with 403 |
| Release evidence collection | `Release.collectEvidence()` is not run live: whether GitLab accepts the request for a release without a pipeline, and what it answers, is unchecked |
| Milestone date serialization | The SDK sends `yyyy-MM-dd` and reads an ISO date back; `MilestonesSmokeIT` is the first check that GitLab accepts it and returns the same date, including for a start date |
| Reaction names GitLab accepts | `ReactionsSmokeIT` reacts with `thumbsup` only; which other names GitLab accepts, and how it answers an unknown name or a second identical reaction, is unchecked |
| Discussion resolvability on issues | Whether a plain issue thread is resolvable depends on GitLab; `DiscussionsSmokeIT` resolves only when the flag says so and otherwise asserts that it is `false` |
| Draft-note publish effects and the 404 after a publish | Publishing a draft note, or all of them, is not run live. That GitLab then answers 404 for the draft note (the SDK's `refresh()` throws `IllegalStateException` on it) is an assumption, as are the notes the publish creates |
| Tag and release creation permissions | Creating a tag or a release needs a role that may do so (Developer or Maintainer, depending on the protected-tag rules of the project); a token of a lower role fails with 403 in `TagsAndReleasesSmokeIT` |
| Group label promotion from a project in a user namespace | `Label.promote()` finds the group from the project's namespace; for a project in a user namespace the SDK sends the promotion and GitLab's rejection passes through. Only a project directly in the sandbox group is run live, and even that has not run yet |
| Same-key variable scope targeting on update and delete | An update and a delete of a project variable send the variable's own scope as `filter[environment_scope]`; whether GitLab then touches only that variable when several share the key is checked first by `VariablesSmokeIT`. A lookup by key alone, when several variables share the key, is not run live, so which one GitLab answers with is unchecked |
| A stale scope on a variable update | GitLab's documentation says that when the scope of the filter does not exist, the endpoint updates a variable with the same key but a different scope; so `update()` on a `Variable` whose scope changed since it was loaded may change another variable. Not run live |
| Group variable scope targeting | GitLab documents a scope filter for the group variable operations, but the core does not offer it, so `GroupVariable` works by key alone; which same-key group variable GitLab loads, changes or deletes is unchecked |
| Hidden and masked variable values | A hidden variable has no `value()` in the SDK (`Optional`), and masking needs a value that GitLab accepts as maskable; neither is run live, because `VariablesSmokeIT` creates plain variables only. What GitLab answers for a masked or hidden variable, and for `maskedAndHidden`, is unchecked |
| Clearing environment fields | `clearKubernetesNamespace()`, `clearFluxResourcePath()` and `clearClusterAgent()` send JSON `null`; that GitLab accepts it and then returns no value is checked first by `EnvironmentsSmokeIT` for the Kubernetes namespace only. The other two are unchecked |
| Deployment status transitions | GitLab accepts only `running`, `success`, `failed` and `canceled` on create and update; which transitions it allows (running to success is run live; others are not), whether it refuses to delete the latest deployment of an environment (the test deletes the older of two), and how long a stopped environment stays `stopping` (the test waits up to 60 seconds for `stopped` before it deletes) are unchecked until `EnvironmentsSmokeIT` runs |
| Runner reads for a token that is not an administrator | Each runner of a project or group list is loaded again through the instance endpoint `GET /runners/{id}`, and `managers()` (`/runners/{id}/managers`) and `jobs()` (`/runners/{id}/jobs`) use it too; whether GitLab answers them for a project Maintainer or only for an administrator is unchecked. `RunnersSmokeIT` skips on a 403 |
| Runner `tag_list` as a JSON array and the other patched runner fields | The core patches its OpenAPI description of the runner records (the `tag_list` array, the registration and detail types, the ids). `RunnersSmokeIT` is where that patch meets a real response: `tagList()`, `type()` and the typed detail fields must parse. It is skipped when the sandbox has no runner, so a sandbox without a runner leaves it unchecked |
| Artifact download permissions | Downloading the artifacts of a job needs access to the job's artifacts (a project that restricts them, or a token of a role that cannot read them, answers 403 or 404), and the download writes a file that is owner-only where the file system has POSIX permissions; `ArtifactsSmokeIT` is skipped when the sandbox has no job with artifacts |
| Package and registry list shapes | The package and container registry lists, the group lists with the `project_id`, the files and the tag details are only unit-tested against records built from the OpenAPI description; `PackagesAndRegistrySmokeIT` is the first check, and it is skipped when the sandbox has no package or repository |
| Schedule inputs on the request side | The core reads inputs of any type in a schedule answer, but sends a scalar input as a one-item array; whether GitLab accepts that for a string, boolean or number input is unchecked, so the SDK offers no schedule inputs (`createPipelineSchedule(payload)` passes the core's payload through) |
| The slug of a renamed wiki page | GitLab derives the slug from the title, so a new title is expected to give a new slug; `WikisSmokeIT` checks that the slug changes and that the new one loads. Whether the old slug then answers 404 or redirects, and how GitLab slugs titles with spaces or other characters, is unchecked |
| The title of a nested page | A page created with the title `smoke-<runId>/page` gets a slug with a slash; whether GitLab then reports the title as the full path or only the last segment (`page`) is unchecked, so `WikisSmokeIT` asserts on the slug only and no unit test relies on the title holding the path |
| Group wiki availability | Group wikis are a Premium feature; on a lower tier GitLab is expected to answer 403 or 404 (the group test of `WikisSmokeIT` then skips). Which of the two a free instance answers, and whether a 404 lookup is then empty, is unchecked |
| The real wiki page shapes | `WikisJsonTest` decodes JSON shaped after the REST docs examples (the page, the list and the attachment), not a live response; `WikisSmokeIT` is the first check against a real answer |
| The default branch of a snippet repository | `fileContent(ref, path)` needs a ref; `SnippetsSmokeIT` reads a file on `main` and skips that check on a 404, so whether a new snippet repository's branch is `main` (or follows the instance default) is unchecked |
| Binary snippet content | The core reads raw snippet content as text, so a binary file comes back decoded as UTF-8 (bytes that are not UTF-8 are lost); not run live |
| Moving a snippet file without content | `moveFile(previousPath, path)` sends the `move` action with `previous_path` and no content; that GitLab then keeps the content of the file is expected, not checked: `SnippetsSmokeIT` checks the new path only |
| The content of a multi-file snippet | `content()` reads `GET .../raw` of the snippet; which file GitLab answers with for a snippet of several files is unchecked (`SnippetsSmokeIT` accepts either file's content) |
| Personal snippet writes | Creating, updating and deleting a personal snippet are not run live (they would write on the token user's account outside the sandbox); they are unit-tested only |
| A project snippet through `sdk.snippets().find(id)` | `GET /snippets/{id}` is expected to return a project snippet the user can see (`response().projectId()` set); its `update()` and `delete()` then go to `/snippets/{id}`, which is not verified for a project snippet and not run live |
| The real snippet shapes | `SnippetsJsonTest` decodes JSON shaped after the REST docs examples (a legacy single-file snippet, a snippet with `files` and the personal list), not a live response |
| Dependency list availability | The list is an Ultimate feature; on a lower tier GitLab is expected to answer 403 or 404 (`DependenciesSmokeIT` then skips). Which of the two a free instance answers is unchecked, and so is whether a sandbox that is Ultimate but has no dependency scan answers an empty list (the test then skips as well) |
| The real dependency shapes | `DependenciesJsonTest` decodes JSON shaped after the REST docs example (vulnerabilities with integer ids, an empty `vulnerabilities` array, a license without `url`), with illustrative values, not a live response. The core patch that turns `vulnerabilities` and `licenses` into arrays meets a real answer only in `DependenciesSmokeIT`, and only when the sandbox has a dependency scan |
| The package manager filter | `all(first, more...)` sends `package_manager` as the core encodes the list; how GitLab treats several values at once is unchecked, and `DependenciesSmokeIT` filters by one value and only checks that the answer is not empty, not that every item has that package manager (unchecked) |
| Keyset paging of audit events | The SDK lists audit events with `pagination=keyset`, `order_by=id` and `sort=desc`, as the REST docs' keyset table lists for project and group audit events; that the instance accepts it (and does not fall back to offset paging or refuse the parameters) is checked first by `AuditEventsSmokeIT`, and only on its first page, because the probe reads five events |
| Fractional seconds in the audit-event bounds | The docs show `YYYY-MM-DDTHH:MM:SSZ`, and whether GitLab accepts a fraction of a second is unchecked, so `createdBetween(after, before)` widens the range to whole seconds: `after` is rounded down and `before` up (`2026-11-14T10:15:30.123Z` as `before` is sent as `2026-11-14T10:15:31Z`). GitLab may return events up to one second outside the requested bounds; filter on `createdAt()` for exactness |
| Audit-event availability | Audit events are a Premium feature; on a lower tier GitLab is expected to answer 403 or 404 (`AuditEventsSmokeIT` then skips). Which of the two a free instance answers, and whether a 404 lookup is then empty, is unchecked |
| A group audit event for a non-owner | The docs make loading one group audit event available to group owners and administrators only; a token without the Owner role is expected to get a 403, which passes through `find(id)` as the core's exception (not an empty result); the group test of `AuditEventsSmokeIT` then skips the lookup. A 404 would make the lookup empty, which would fail an assertion on the event; the group test therefore skips on an empty lookup too (the project test does not: its event was just listed). Unchecked |
| The real audit-event shapes | `AuditEventsJsonTest` decodes the REST docs examples verbatim (the project list and the group event, with a numeric and a text `target_id`), not a live response; the docs examples have no `event_name`, so its shape is unchecked |

## Reading a failure

A failing smoke test means the SDK and the live API disagree. A 401 means the token is wrong or expired, a 403 that the
token lacks the `api` scope or the user lacks the role the call needs (protecting a branch needs Maintainer), and a 404
on the sandbox that `SMOKE_GITLAB_PROJECT` or `SMOKE_GITLAB_URL` is wrong.
